# FRP 平台 0.1.0 详细安装与使用手册

适用交付：第一阶段 Go/Vue/PostgreSQL 时长卡与 TCP/UDP 平台。先阅读 [验收与限制](验收与限制.md)，区分已经实测、仅交叉编译及尚未实现的功能。本手册包含可操作部署步骤；其中 Linux/systemd 与 Docker 因本环境没有相应运行条件，尚未完成实机安装验收。

## 1. 角色、组件与准备工作

- **控制平台**：存账号、套餐、卡密摘要、兑换记录、设备与隧道配置；同时提供用户中心及后台。需要 PostgreSQL。
- **转发节点**：必须具有可被用户和访客访问的公网入口，运行 `portal node`、守护和官方 frps。每台设备一个控制端口，每条隧道一个业务端口。
- **客户端**：安装官方 frpc 与 `portal`，运行 CLI Agent；位于用户服务所在的内网电脑或能访问目标服务的主机。
- **超级管理员**：首次 `bootstrap` 创建，登录需要密码和 TOTP 动态码；管理写操作再次提供密码及动态码。
- **用户**：注册、兑换、绑定设备、管理自己的 TCP/UDP 隧道。

最低建议：控制平台 2 vCPU / 2 GiB 内存、PostgreSQL 独立磁盘；节点资源按独立 frps 进程数和实际连接压力评估，本版没有给出经过压测的容量承诺。小规模可把控制和节点部署在同一台公网 Linux 主机；数据库与管理接口必须保留在私网或回环。测试客户端可为 Windows x64。

准备两个名称示例：`portal.example.com` 指向控制平台 HTTPS 入口，`node.example.com` 指向节点公网 IP。示例域名须替换成你实际持有的域名。节点 DNS 的 A/AAAA 记录必须与你真正开放的 IPv4/IPv6 网络一致；仅有内网 IP/运营商 CGNAT 的服务器不能因安装软件就变成公网入口。需要公网 IP、已有公网转发入口或相应端口映射。

端口规划示例：

| 用途 | 示例 | 防火墙/云安全组 |
|---|---|---|
| 控制台 HTTPS | TCP 443；自动签证时 TCP 80 | 对用户/节点开放；80 根据签证方式决定 |
| Go 私有控制 HTTP | TCP 8080 | 仅反代可达；不直接映射公网 |
| PostgreSQL | TCP 5432 | 仅控制平台私网/回环可达 |
| 节点设备控制池 | TCP 17000–17099 | 对客户端开放；可按客户来源 IP 收紧 |
| 节点业务池 | TCP/UDP 20000–20999 | 按实际套餐开放；TCP 与 UDP 分开写规则 |
| 本地插件 | 每设备随机回环 TCP 端口 | 禁止公网访问，不建立安全组规则 |
| SSH/RDP 运维 | 运维自定义端口 | 仅管理 IP/VPN 可达 |

只开云安全组还不够，系统防火墙也要放行。IPv6 还要检查运营商、客户端、DNS 和系统监听地址，本版默认 frps `0.0.0.0`，**未实现 IPv6 转发部署验收**；不要仅添加 AAAA 就承诺 IPv6 可用。控制池和业务池必须互不重叠，也不能占用平台的 443/8080 等端口。本版自动分配仅识别平台数据库占用，外部程序占用会在实际 frps 启动时失败并记日志；部署前应使用 `ss -lntup` / `Get-NetTCPConnection` 和 `Get-NetUDPEndpoint` 检查。

所有机器启用可信 NTP。平台、数据库和节点使用 UTC 语义；数据库字段为 timestamptz，浏览器按当前浏览器时区显示。建议 Linux `timedatectl set-ntp true`；Windows 检查 `w32tm /query /status`。

## 2. 获取源码、构建与校验

源码根目录为 `frp-business`。已经附带 Windows amd64、Linux amd64、Linux arm64 的 portal 构建产物。源码构建需要 Go 1.27.3、Node.js 22.22.0/npm；FRP 下载脚本需要 Python 3.12+。生产使用的 PostgreSQL 安装请遵循官方对应系统文档并设置独立应用账号；不要使用测试中的 trust 鉴权。

Windows：

```powershell
Set-Location C:\path\to\frp-business
.\scripts\build.ps1
python .\scripts\fetch-frp.py --os windows --arch amd64 --out C:\FRP\upstream
```

Linux：

```bash
cd /path/to/frp-business
bash scripts/build.sh
python3 scripts/fetch-frp.py --os linux --arch amd64 --out ./upstream
# ARM64 主机把 amd64 改成 arm64。
```

`dist/<os>-<arch>/portal[.exe]` 是平台程序。FRP 位于 `upstream/frp_0.71.1_<os>_<arch>/`。下载脚本从锁文件选择唯一 URL，校验固定 SHA256 再解压。不要使用来源不明的自动下载地址，也不要把 frps/frpc 从其他版本混进来；运行节点/Agent 时会检查 `--version` 必须是 0.71.1。

### 发布签名与首次信任

每个 dist 平台目录有 `SHA256SUMS` 和 `.sig`。交付的 `release-public.key` 对应本次本地打包签名，仅提供交付完整性检验，**不表示已经建立运营方的可信发布身份**。首次可信 `portal` 应从已审阅源码构建，或通过独立可信渠道核对二进制 SHA256；不要用一份来路未知的二进制验证它自己。

```powershell
# 使用已可信的旧版本或从源码构建的程序进行验证。
C:\trusted\portal.exe verify --key .\release-public.key --manifest .\dist\windows-amd64\SHA256SUMS
Get-FileHash .\dist\windows-amd64\portal.exe -Algorithm SHA256
```

Linux 对应：

```bash
/trusted/portal verify --key release-public.key --manifest dist/linux-amd64/SHA256SUMS
sha256sum dist/linux-amd64/portal
```

运营方应生成自己的**离线发布密钥**，与控制平台租约签名种子分开：

```bash
portal release-keygen --dir /offline/release-keys
# 在待发布目录写入平台二进制校验和。清单每行：64位SHA256 + 两个空格 + 文件名。
sha256sum portal > SHA256SUMS
portal release-sign --key /offline/release-keys/release-private.key --manifest SHA256SUMS
portal verify --key /offline/release-keys/release-public.key --manifest SHA256SUMS
```

私钥不进入镜像、源码仓库、用户下载包或安装脚本。本版不自动更新；安装升级先验签、备份、替换再健康检查。多节点灰度升级先人工选择单个节点完成 E2E，再逐批推广。

## 3. 安装 PostgreSQL 与初始化控制配置

创建专用数据库和账号。下面在已有 PostgreSQL 管理终端执行（密码自行生成，不要原样使用占位符）：

```sql
CREATE ROLE portal LOGIN PASSWORD '<随机强密码>';
CREATE DATABASE portal OWNER portal ENCODING 'UTF8';
```

应用账号需要在自己的库里建表/索引/迁移权限，不需要超级用户权限。不同主机访问数据库应配置私网 ACL 和 `sslmode=verify-full` 与受信根证书；手册中的 `sslmode=disable` 仅适用于本机回环演示，不能推广到公网。

Windows PowerShell 隐藏读取数据库 DSN，再初始化：

```powershell
$dsnSecret = Read-Host '数据库连接串' -AsSecureString
$env:FRP_DATABASE_URL = [Net.NetworkCredential]::new('', $dsnSecret).Password
.\portal.exe init --dir C:\FRP\control --public-url https://portal.example.com
Remove-Item Env:FRP_DATABASE_URL
```

Linux：

```bash
umask 077
read -r -s -p '数据库连接串: ' FRP_DATABASE_URL; echo
export FRP_DATABASE_URL
./portal init --dir /etc/frp-portal/control --public-url https://portal.example.com
unset FRP_DATABASE_URL
```

连接串示例结构：`postgres://portal:<URL编码密码>@127.0.0.1:5432/portal?sslmode=disable`。若密码包含 `@ : / # %` 等字符，必须 URL 编码，不能直接拼接。`init` 生成随机 `signing_seed`，不会覆盖已有配置；务必离线备份该种子及数据库。命令输出的节点验证公钥可以公开，私有 seed 不可公开。

控制配置中填生产 HTTPS 证书绝对路径，例如：

```json
{
  "listen": "127.0.0.1:8080",
  "database_url": "postgres://portal:URL_ENCODED_PASSWORD@127.0.0.1:5432/portal?sslmode=disable",
  "public_url": "https://portal.example.com",
  "tls_cert": "/etc/frp-portal/control/fullchain.pem",
  "tls_key": "/etc/frp-portal/control/privkey.pem",
  "signing_seed": "由 init 生成的值"
}
```

这份直接 TLS 示例仅监听回环，公网前还需要 TCP/TLS 代理或将 `listen` 明确设置为 `0.0.0.0:443` 并配置适当监听权限。本版 Linux 服务账号不是 root，不直接绑定 443；推荐下一节的 Caddy 终止 HTTPS，Go 监听私有 8080。使用反代时删除 Go 证书字段，设置 `reverse_proxy_tls: true`，不要同时开开发模式。

执行迁移与创建初始管理员：

```powershell
.\portal.exe migrate --config C:\FRP\control\control.json
$adminSecret = Read-Host '管理员密码（至少12字节）' -AsSecureString
[Net.NetworkCredential]::new('', $adminSecret).Password | .\portal.exe bootstrap --config C:\FRP\control\control.json --email owner@example.com
Remove-Variable adminSecret
```

```bash
./portal migrate --config /etc/frp-portal/control/control.json
read -r -s -p '管理员密码: ' ADMIN_PASS; echo
printf '%s\n' "$ADMIN_PASS" | ./portal bootstrap --config /etc/frp-portal/control/control.json --email owner@example.com
unset ADMIN_PASS
```

`bootstrap` 仅能创建第一次超级管理员，数据库存在 super 后拒绝再次执行。输出一次性的 TOTP 密钥和 otpauth URL，录入认证器并离线备份；不要保存到公共工单或日志。管理员密码长度为 12–72 字节（bcrypt 限制）。本版没有自动邮件找回和 TOTP 恢复流程，丢失应通过受审计的数据库运维流程处理，不能重新 bootstrap 覆盖用户。

## 4. 压缩包/前台方式首次启动

先用前台启动，确认错误清楚后再注册服务：

```powershell
.\portal.exe serve --config C:\FRP\control\control.json --log-file C:\FRP\control\control.log
```

```bash
./portal serve --config /etc/frp-portal/control/control.json --log-file /var/log/frp-portal/control.log
```

日志父目录需预先创建并允许服务账号写入。浏览器访问 `public_url`，`GET /healthz` 应返回 `status: ok`。没有配置生产 TLS 或明确的私有 TLS 反代时程序拒绝启动。

仅本机开发调试可使用：

```json
{"listen":"127.0.0.1:8080","public_url":"http://127.0.0.1:8080","dev_http":true,"database_url":"本机测试数据库DSN","signing_seed":"init生成的值"}
```

开发模式只允许回环监听。不要把 dev_http=true 与公网反代组合，本版 Cookie 在开发模式不加 Secure。浏览器访问的 scheme/host/port 必须与 public_url 完全匹配，否则 Origin 检查拒绝写操作。

## 5. Docker Compose 部署控制平台

本环境无 Docker，以下文件已提供、基础镜像 tag/digest 已核实，但构建/启动步骤须在你的 Linux Docker 主机验收。不要把文档命令当作已经实机通过的结果。

1. 安装 Docker Engine 与 Compose v2，准备公网域名 A 记录。
2. 进入 `deploy`，创建权限 600 的 `.env`，内容为运营方随机生成的 `POSTGRES_PASSWORD` 和实际 `PORTAL_DOMAIN`。数据库密码推荐随机十六进制，便于 DSN 编码。
3. `docker compose build`，然后 `docker compose up -d postgres`。
4. 在主机用可信 `portal init` 生成 `deploy/config/control.json`，数据库主机改为 `postgres:5432`，数据库/用户均为 `portal`，密码与 `.env` 一致。
5. config 中设置 `listen: "0.0.0.0:8080"`、`public_url: "https://实际域名"`、`reverse_proxy_tls: true`，不设置 dev_http，不设置 Go TLS 文件。
6. 配置只挂载给控制容器，非 root UID 10001 需要读权限，可使用专用组或 `chown 10001:10001 config/control.json && chmod 600 config/control.json`。不要改为全球可读。
7. 执行迁移和 bootstrap，再启动 Caddy 与控制台。

```bash
cd deploy
docker compose build
docker compose up -d postgres
docker compose run --rm control migrate --config /config/control.json
read -r -s -p '管理员密码: ' ADMIN_PASS; echo
printf '%s\n' "$ADMIN_PASS" | docker compose run --rm -T control bootstrap --config /config/control.json --email owner@example.com
unset ADMIN_PASS
docker compose up -d
docker compose ps
docker compose logs --tail=100 control
curl --fail https://portal.example.com/healthz
```

Caddy 自动 HTTPS 要求域名正确、80/443 可达及证书机构可访问。PostgreSQL 和控制 HTTP 不发布宿主端口，Caddy 是唯一公网入口。`reverse_proxy_tls` 是对部署者的明确配置约定，程序不会自动判断反代来源安全；网络隔离必须正确。

镜像内含锁定的 frps/frpc，但节点独立部署。Linux 节点可使用 `deploy/node-compose.yaml` 的 host 网络模板；先创建 `node-config`、`node-state`，让 UID10001 读证书/配置并写 state。本版不推荐把 Windows Docker Desktop 的 host 网络当作生产节点；尚未验证。

## 6. 管理员创建节点和套餐

访问控制台，用管理员邮箱、密码、当前 6 位 TOTP 登录。左侧有运营菜单；普通用户看不到且 API 也会拒绝。

在“套餐与节点”顶部输入管理员密码和当前动态码。这些字段仅保存在页面内存，刷新后消失。TOTP 每 30 秒更新，过期后重新输入。

“添加转发节点”填写：

- 节点名称：例如“上海 01”。
- 公网主机名：`node.example.com`，不带 `https://` 和端口。
- 控制端口范围：例如 17000–17099，共 100 个设备槽位。
- 业务端口范围：例如 20000–20999。

创建成功后只返回一次 `node_id`、节点 `credential` 与 `verify_key`，立即安全保存。数据库只存节点 credential 摘要，无法从后台再次导出。若响应丢失，不要猜密钥；将该节点停用，创建新节点并按显式迁移流程处理，本版没有节点原位凭据轮换界面。

“创建固定规则套餐”选择节点、设备数上限、账号总隧道数、单隧道 KiB/s 及参考价格。例：1 台设备、3 条隧道、每隧道 1024 KiB/s，约每隧道 8.39 Mbps。**三条隧道可以合计约三倍单隧道速率，本版没有账号总速率限制**。数量是未撤销绑定设备数，不是瞬时在线设备数；不销售并发连接数限制产品。

套餐规则固定，改规则新建套餐，不修改历史快照。价格“分”只是参考字段，不会自动产生订单或支付收款。

## 7. 安装转发节点

复制 `portal` 与锁定 FRP 的 `frps` 到节点，准备 `node.example.com` 的有效证书。证书可由运营方现有 ACME/证书系统提供，本版不自动申请/续期。证书中的 SAN 必须匹配节点 host；私钥仅节点服务账号可读。

Linux `node.json` 示例：

```json
{
  "control_url": "https://portal.example.com",
  "node_id": "创建节点返回的node_id",
  "credential": "创建节点返回的credential",
  "verify_key": "创建节点返回的verify_key",
  "frp_path": "/opt/frp-upstream/frps",
  "tls_cert": "/etc/frp-portal/node/fullchain.pem",
  "tls_key": "/etc/frp-portal/node/privkey.pem",
  "state_dir": "/var/lib/frp-portal/node"
}
```

Windows 对应路径示例：

```json
{
  "control_url": "https://portal.example.com",
  "node_id": "返回的node_id",
  "credential": "返回的credential",
  "verify_key": "返回的verify_key",
  "frp_path": "C:/ProgramData/FRPPortal-node/upstream/frps.exe",
  "tls_cert": "C:/ProgramData/FRPPortal-node/node.crt",
  "tls_key": "C:/ProgramData/FRPPortal-node/node.key",
  "state_dir": "C:/ProgramData/FRPPortal-node/state"
}
```

JSON 推荐用正斜杠表示 Windows 路径，避免反斜杠转义错误。先运行：

```bash
portal node --config /path/node.json --log-file /path/logs/node.log
```

后台节点“最近通讯”应每约 2 秒更新。尚无用户设备和隧道时不会启动设备 frps、也不会监听全部控制池，这属于正常行为。

如果控制台证书来自私有 CA，node.json 还需要 `ca_file` 指向可信 CA PEM；公开 CA 通常使用系统证书库。节点用于自身 frps 的证书与控制平台的 HTTPS 证书是两条不同链路。

仅本机 E2E 可用 `portal dev-cert --dir <测试目录> --host localhost` 生成 30 天开发证书；已有证书/私钥不会被覆盖。正式运营不要使用这个开发证书。

## 8. 批量生成、分发、禁用充值码

在“充值码管理”选择套餐，设置批次名称、备注、时长、数量、兑换截止时间。页面截止时间明确按 **UTC** 输入，例如北京时间 2026-11-01 08:00 对应 UTC 2026-11-01 00:00。

支持 1 小时、1/7/30/90/365 天，或输入自定义秒数。一天固定 86400 秒，30 天固定 2592000 秒；没有“自然月”卡。每批最多 1000 张。

点击“生成并一次性导出”，马上下载卡密文本。服务器不长期保存卡明文，刷新页面后无法再次导出；导出与生成属于同一有审计的事务。请使用受控的售卡/交付渠道，不要贴到公共群聊。本版没有在线售卡支付或代理商发卡系统。

若生成响应丢失，不能简单认为生成失败；刷新批次列表确认，禁用那批未兑换卡，再重新发卡。卡密生成接口目前不支持请求幂等，**兑换接口支持**。导出文件应加密存储，做好发售状态与财务的独立对账。

“禁用未兑换卡”只禁用未使用卡，不删除已经发放权益或历史。退费/误发需要在“用户与权益”输入正/负秒数与明确原因，留下独立调整流水。

## 9. 用户注册、兑换、查看有效期

1. 用户访问控制台，点击注册，输入邮箱和至少 12 字节密码。
2. 当前阶段注册邮箱只作为账号名，不发送验证邮件；登录普通用户不需要 TOTP。
3. 进入“充值续费”，粘贴卡密，分隔短横线、大小写和空格会归一化。
4. 首次兑换立即激活。相同套餐续费公式：`max(当前有效期,服务器当前时间)+卡时长`。
5. 同用户同卡重复提交只返回原结果，不重复加时；卡不能被另一个账号使用。
6. 当前有套餐记录时不允许换另一套餐，即使已过期也拒绝，联系管理员做独立迁移；不静默覆盖。
7. “服务概览”显示套餐、到期时间、剩余时长、节点最近通讯；三天内到期显示站内提示。时间在刷新时更新，邮件通知未实现。

有效期按自然经过时间消耗，客户端断网、关机、离线或隧道暂停都不会冻结。续费只增加到期时间，不会重置任何流量；本版根本没有已收费的流量配额账本。发生节点故障，管理员用独立权益调整进行补偿。

## 10. Windows/Linux 客户端绑定与运行

用户从运营方可信渠道获得对应平台 portal、官方 frpc、必要的节点 CA 文件。客户端配置必须包含 `ca_file`；使用公开证书时可使用覆盖对应公开根的 PEM 信任链，不能关闭证书校验。控制 API 同时用系统证书库并按配置附加该 CA。

用户中心“我的设备”输入设备名称并生成绑定码。5 分钟内有效、仅可使用一次，随机 160 位；不要把完整设备配置发给其他人。

Windows `agent.json`：

```json
{
  "control_url": "https://portal.example.com",
  "frp_path": "C:/FRP/frpc.exe",
  "state_dir": "C:/FRP/state",
  "ca_file": "C:/FRP/node-ca.pem"
}
```

```powershell
.\portal.exe bind --config C:\FRP\agent.json
# 按提示输入一次性绑定码
.\portal.exe agent --config C:\FRP\agent.json --log-file C:\FRP\logs\agent.log
```

Linux 把路径替换为绝对路径，流程相同：

```bash
chmod 600 /etc/frp-portal/agent.json
portal bind --config /etc/frp-portal/agent.json
portal agent --config /etc/frp-portal/agent.json --log-file /var/log/frp-portal/agent.log
```

绑定成功会把独立设备 ID 和凭据写回 agent.json，因此绑定时配置文件需可写。之后服务以只读配置启动，状态目录独立可写。文件权限应限制当前用户、管理员及服务账号；Windows `chmod 600` 不能代替 ACL，请使用安装脚本或 `icacls`。

CLI Agent 每约 3 秒获取配置，失败退避到 2/4/8/16 秒并加随机抖动；FRP 自身内部登录重试沿用上游机制，尚未为其每个内部重试引入平台自定义抖动。控制 API 失败时合作式 Agent 主动停止 frpc；节点也独立实施失效，原生/修改客户端不能绕过。

“撤销凭据”会停止设备转发且旧 API token 永久失效。更换设备采用撤销旧设备后重新生成绑定码，本版不提供原位密钥轮换按钮。撤销不删除历史隧道，需自行删除旧隧道释放隧道额度及业务端口；新设备重新创建隧道。

## 11. 创建、暂停、编辑和验证隧道

在“隧道管理”选择已绑定设备、TCP/UDP、本地服务地址和端口。远程端口填 0 由平台分配，或填节点业务端口池内指定端口。协议、设备和远程端口创建后固定；修改它们请删除后新建。页面可暂停/恢复/删除，名称与本地地址编辑目前通过 API PATCH，示例见 API 文档。

常见模板：

| 场景 | 协议/本地端口示例 | 访问方式 |
|---|---|---|
| SSH | TCP / 22 | `ssh -p 远程端口 user@node.example.com` |
| Windows 远程桌面 | TCP / 3389 | mstsc 连接 `node.example.com:远程端口` |
| NAS Web 管理 | TCP / NAS 实际端口 | `https://node.example.com:远程端口`，证书域名按业务服务实际配置 |
| 普通网站 | TCP / 80 或 443 | TCP 端口转发；不是本版已实现 HTTP 虚拟主机 |
| 游戏/语音 | 按应用要求 TCP 或 UDP | 使用应用客户端连接节点和分配端口；多端口分别创建 |

本地服务地址是从 **frpc 所在客户端** 看过去的地址，通常 127.0.0.1；不是控制服务器的地址。将本地服务设为局域网其他地址意味着授予该设备转发对应内网服务的权限，运营方应有明确授权政策。公网暴露 SSH/RDP/NAS 前先配置业务自身强密码、更新、访问白名单；本版没有隧道级 IP ACL 界面，应在节点防火墙实施。

平台返回“已保存”只表示数据库事务成功。Agent/节点日志有 `config_version` / `grant applied`，但本版还没有把下发/应用回执持久回传到 UI，**不能把页面“已保存”当成已经连通**。创建/更改通常 2–5 秒获取；服务重启和上游重连可能增加时间。

TCP 实测：先本地启动 `python -m http.server 8081 --bind 127.0.0.1`，创建 TCP→8081 隧道，从另一网络运行 `curl http://node.example.com:远程端口/`。使用 Python 测试服务器仅用于临时验证，不把它当生产网站。

UDP 必须用实际 UDP 应用发送请求并收到响应；`telnet`/`curl http://` 只能验证 TCP，不能证明 UDP。交付的 `tests/e2e.py` 会真正启动 UDP echo 服务并验证响应。

暂停、删除和节点配置改变会重启该设备 frps，**同设备其他隧道的已有连接也可能中断**；不承诺 TCP 无损迁移。套餐到期、封禁、撤销、维护和控制故障下授权最多保留到有限租约（正常运行条件下产品上限16秒）。续费后原生 frpc 会尝试重连，Agent 会重新获取配置；可能需要等待指数退避最多约 16.5 秒。

## 12. 注册开机服务与异常重启

### Linux systemd

安装脚本只接受已验签目录，固定安装根 `/opt/frp-portal/<mode>`，服务账号 `frpportal`，状态目录 `/var/lib/frp-portal/<mode>`。先将 node/agent 配置中的 state_dir 改为这个路径，frp_path 和证书路径应处于服务可读位置。禁止把 root 的家目录作为证书路径，因为服务启用了 ProtectHome。

```bash
sudo bash scripts/install-linux.sh --source "$PWD/dist/linux-amd64" \
 --verifier /trusted/portal --public-key "$PWD/release-public.key" \
 --config /etc/frp-portal/node.json --mode node
systemctl status frp-portal-node
journalctl -u frp-portal-node -n 100 --no-pager
```

serve/node/agent 分别执行一次，配置彼此独立。重复运行保留已有 config.json，备份配置，并将旧版本留在 releases 和 previous。启动失败自动切回旧二进制（若存在）；启动后仍需真实流量及健康验收，单纯 systemd active 不是完整健康检查。

服务默认异常重启，限制写入范围、禁用提权、私有临时目录。证书/FRP 二进制应 root 持有、frpportal 只读。不要授予服务账号改写程序的权限。

### Windows Service

管理员 PowerShell 运行安装。安装根为 `%ProgramData%\FRPPortal-<mode>`；运行账号为 LocalService；state/logs 可写，配置与程序只读。配置中的 `state_dir` 必须提前设为相应 `state`，外部 frp_path、证书文件应给予 LocalService 读取权限。节点示例路径见上文。

```powershell
.\scripts\install-windows.ps1 -Source .\dist\windows-amd64 `
 -Verifier C:\trusted\portal.exe -PublicKey .\release-public.key `
 -Config C:\FRP\node.json -Mode node
Get-Service FRPPortal-node
Get-Content C:\ProgramData\FRPPortal-node\logs\node.log -Tail 100
```

安装脚本不打开防火墙、不上传证书、不硬编码凭据。外部证书缺少 ACL、state_dir 写权限错误等，会导致失败，查看日志修正。无需桌面交互窗口；不建议给 Windows 服务使用映射网络盘符，因为服务会话可能看不到。

所有 portal 日志通过 `--log-file` 轮转：当前文件最多约10MiB，另保留3份，4份合计约40MiB；单条超大消息可能超出边界。frps 自身每设备日志在 state_dir，保留7天，按上游日志机制轮转。本版 frpc stdout 进入 Agent 日志，不记录业务载荷。日志可能包含设备 ID、地址、端口和运行错误，仍需访问控制与保留策略。更复杂的日志保留周期、告警订阅和日志采集尚未提供。

## 13. 备份、恢复与卡密对账

至少备份：PostgreSQL 全库、control.json 中租约签名种子、节点配置/证书/私钥、发布公钥、版本和安装目录。售卡导出文件单独加密备份并记录销售状态。不要只复制运行中的 PostgreSQL 数据目录。

```bash
# 使用 .pgpass / 服务账号凭据，避免在进程参数和 shell 历史中放密码。
pg_dump -h 127.0.0.1 -U portal -Fc portal -f portal-UTC_TIMESTAMP.dump
sha256sum portal-UTC_TIMESTAMP.dump > portal-UTC_TIMESTAMP.dump.sha256
pg_restore --list portal-UTC_TIMESTAMP.dump
```

备份必须加密、异地保留，并在隔离库实际恢复演练。高要求运营应配置 PostgreSQL WAL 归档/PITR，而不是依赖每日一次逻辑备份。上述模板没有自动化开通 WAL/PITR。

**恢复旧备份可能把已经兑过的卡重新变成未使用。必须在恢复服务之前完成以下对账：**

1. 停止公网入口的兑换/发卡，停控制服务和节点，保存事故时数据库、WAL、审计及发卡记录；不要立即覆盖唯一现场。
2. 在隔离新库 `pg_restore`，迁移版本与程序版本匹配，保留原签名 seed。
3. 优先使用完整 WAL/PITR 恢复到事故前状态。若存在事故后外部完整流水，依据唯一卡 hash、兑换 ID、request_id 与权益调整按审计流程重放。
4. 查不到完整增量时，**默认禁用所有恢复库中尚未兑换卡，且暂停发卡**，逐批核对并重发未消费卡。禁止直接上线旧库让旧卡再次兑换。
5. 对账每个用户最后兑换、调整及 expires_at；核对批次总数、已兑数、售卡账、管理审计。不要用“已兑次数×套餐参考价”替代财务收入。
6. 逐项复测同卡不可重复、到期停止、节点授权，再开放入口。

隔离恢复库中保守禁用示例（维护账号执行，另记录事故工单和数据库操作审计）：

```sql
BEGIN;
UPDATE cards SET disabled=true
 WHERE NOT EXISTS(SELECT 1 FROM redemptions r WHERE r.card_hash=cards.hash);
COMMIT;
```

本版没有完整的外部防回滚账本、自动恢复对账器或事故后流水重放工具，**不能声称恢复旧备份会自动避免重兑**。要以恢复演练作为收费运营前验收项。

## 14. 升级、失败回滚和证书续期

1. 读取新版本迁移说明、FRP 兼容说明和许可证变化，备份数据库/配置/证书。
2. 使用离线信任公钥验签新目录，不关闭校验。
3. 先单节点灰度，维护状态下停止新授权；通知设备连接会中断。
4. 重复安装脚本，旧配置不覆盖，保留旧二进制路径。手动变更配置需单独备份并比较。
5. 验证 `/healthz`、后台节点通讯、真实 TCP/UDP、卡兑换幂等及失效。
6. 验收不通过切回旧二进制；**不能在未知数据库迁移上盲目回滚**。本版只有幂等 v1，读到高于1的 schema_versions 会拒绝降级；未来破坏性迁移需发布专门回滚/前滚策略。

Linux 手动回滚二进制示例：

```bash
sudo systemctl stop frp-portal-node
previous=$(readlink /opt/frp-portal/node/previous)
test -n "$previous" && test -x "$previous/portal"
sudo ln -sfn "$previous" /opt/frp-portal/node/current
sudo systemctl start frp-portal-node
```

Windows `previous-service-path.txt` 保留旧路径，可在管理员 PowerShell 读取并用 `sc.exe config FRPPortal-node binPath= $oldPath` 恢复，再启动服务。若旧版本不存在，修正配置后重装，不伪造“已自动回滚成功”。

节点证书到期前由外部证书系统续期，保持私钥 ACL，维护窗口重启节点让设备 frps 加载新证书。更换自签/私有根 CA 需先向客户端发新信任链，验签配置分发尚未提供自动更新；不能直接删除客户端旧根导致大面积断连。公开证书更新保持可信链与 SAN，仍须测试。

## 16. 故障排查表

| 现象 | 检查与处理 |
|---|---|
| 控制台 502 | Go 服务是否运行、反代目标端口、数据库连通、控制日志；先访问私有 healthz |
| 登录/写操作“来源校验失败” | public_url 与浏览器实际 origin 是否完全一致；不要混 localhost、127.0.0.1 或不同端口 |
| 管理员 OTP 错误 | 双方 NTP、认证器 SHA1/6位/30秒，输入当前码；检查登录邮箱是否管理员 |
| Cookie 登录后立即失效 | 生产 HTTPS 是否真的启用，Secure Cookie、反代公网 URL，禁止公网使用 dev_http |
| 充值码不存在/不可用 | 检查复制完整32个 Base32 字符、批次是否禁用、截止UTC、是否被他人兑换 |
| 换套餐被拒绝 | 本阶段仅同套餐，联系管理员独立迁移；禁止直接手改 plan_id 绕过历史规则 |
| 绑定失败 | 码是否5分钟内、是否已用、套餐到期/节点维护、设备上限；撤销不用的设备 |
| 节点无控制监听 | 无设备/启用隧道时正常；检查授权、端口冲突、frps版本、TLS路径和权限 |
| TLS x509 错误 | CA文件、节点SAN与host、证书有效期、系统时间；不要设置 InsecureSkipVerify |
| TCP 连接但应用无响应 | portal diagnose，本地服务地址/端口，应用自身防火墙；节点日志是否插件拒绝 |
| UDP 不通 | UDP系统/云防火墙、实际应用层响应、报文大小；TCP端口检测不能验证UDP |
| frps bind address already in use | 外部程序抢占或前一实例尚未释放；查系统端口、改池/维护，数据库只能避免平台内并发重复分配 |
| 节点持续租约签名错误 | verify_key 与原控制seed是否匹配，控制备份是否恢复错，节点/平台NTP |
| 到期续费后仍不恢复 | frpc/Agent 退避、节点/控制通讯、设备是否撤销、是否同套餐，等待最多一轮退避再查日志 |
| HTTP 429 | 登录/注册每IP每接口12次/分、每账号登录8次/分；兑换每用户10次/分；共享NAT可受影响，边缘限流需单独配置 |
| Windows 服务启动失败 | LocalService可读配置/证书/frp，state/logs可写、绝对路径，检查程序轮转日志 |
| Linux 服务启动失败 | systemctl/journalctl，权限、ProtectHome、ReadWritePaths、Go/FRP架构、非root不可绑低端口 |

诊断命令：

```bash
portal version
portal diagnose --config /path/agent.json
```

diagnose 检查控制凭据/权益、节点DNS、控制TCP、本地TCP服务。不会假装验证UDP业务、全链路TLS握手或公网业务端口的全部条件。数据面控制与前端状态不一致时，以节点日志和真实业务测试为准。
